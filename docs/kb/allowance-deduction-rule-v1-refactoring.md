# 手当・控除マスター／Rule連携 V1リファクタリング

## 1. 目的

手当・控除マスターを、複雑な給与項目を管理画面から設定できる基盤として安定化する。

## V1リリース前の解消課題

手当・控除の従業員別設定、日報入力、明細取引、残高表示はマスター駆動へ移行済みである。

- 従業員画面への項目表示には、手当／控除マスターと対応する`payroll_item_balance_policy`を登録する。
- `EMPLOYEE_ENROLLMENT`を指定した項目は、従業員の「手当・控除設定」へ自動表示する。
- 入力欄は`payroll_item_parameter_definition`から動的生成し、項目コードによる画面分岐は追加しない。
- 会社固有の基準値が必要な場合だけ、汎用Resolver SPIの実装を会社固有領域へ追加する。

推奨する最終形：

1. 手当・控除マスターで計算方式、表示対象、入力可否を定義
2. ポリシーマスターで入力元、残高追跡、単位、繰越方法を定義
3. パラメーター定義で従業員別入力欄の型、選択肢、初期値、必須条件を定義
4. 従業員画面と日報画面は上記定義から動的生成
5. 旧`dormitoryFlag`、`dormitoryType`、`dormitoryChargeDays`はDB移行・旧API互換のみに限定

本対応では、マスター定義、Rule選択、計算区分の整合性、権限、法定控除の根拠データ参照を対象とする。

## 2. V1で確定した仕様

### 2.1 権限

| 権限 | 操作 |
|---|---|
| `master:view` | 一覧、詳細、法定控除の根拠テーブル参照 |
| `master:manage` | 新規登録、更新、削除、Rule候補取得 |

- 閲覧対象者は固定Role名で判定せず、Role管理から `master:view` を付与する。
- 更新対象者はRole管理から `master:manage` を付与する。
- 初期状態では `SYS_ADMIN` が全権限を持つ。
- Role管理で一般利用者へ `master:view` を割り当てることで、全利用者が閲覧できる。

## 2.2 マスターコード

- 英大文字で開始する。
- 使用可能文字は英大文字、数字、アンダースコアとする。
- 最大50文字とする。
- 入力値は登録時に大文字へ正規化する。
- 作成後は変更不可とする。
- 削除は物理削除せず、`enabled=false` と `deleted_at` を設定する論理削除とする。
- 過去の日報・給与明細に保存済みのコードおよび名称スナップショットは変更しない。
- 論理削除済みコードは履歴識別子として予約し、再利用しない。

## 2.3 計算区分

| 計算区分 | 必須条件 | Rule |
|---|---|---|
| `MANUAL` | 手入力許可が有効 | 保存しない |
| `FIXED` | 固定金額が必須 | 保存しない |
| `AUTO` | 有効なRuleの選択が必須 | 選択したRule名を保存 |

共通制約：

- 初期金額、下限金額、上限金額、表示順は0以上。
- 下限金額は上限金額以下。
- `AUTO` 以外へ変更した場合、既存の `rule_name` は自動的に消去する。
- `AUTO` 保存時には、同一テナント内に有効かつ未削除のRuleが存在することをサーバー側で再検証する。
- Rule実行結果が負数、非数、無限値の場合は計算エラーとする。
- Rule実行失敗時は、給与項目コードとRule名を含む業務エラーへ変換する。

### 2.3.1 手動変更の確定仕様

計算区分と手動変更可否は別の設定として扱う。

| 計算区分 | 基準金額 | `allow_manual_input=false` | `allow_manual_input=true` |
|---|---|---|---|
| `MANUAL` | 利用者入力 | 設定不可 | 入力可能 |
| `FIXED` | マスターの固定金額 | 変更不可 | 基準金額を手動変更可能 |
| `AUTO` | Rule計算結果 | 変更不可 | Rule計算結果を手動変更可能 |

- `FIXED`と`AUTO`を手動変更した場合は、基準金額、最終金額、変更理由を明細へ保存する。
- 手動変更時の変更理由は必須とし、最大500文字とする。
- 日報保存時にはクライアント送信値だけを信用せず、サーバーで基準金額を再計算してから手動変更を適用する。
- 手当・控除の両明細に、基準金額、最終金額、手動変更フラグ、変更理由を同じ形式で保存する。

## 2.4 Rule選択

- Rule名の自由入力を廃止する。
- マスター編集画面では有効なRuleだけをプルダウン表示する。
- プルダウン表示は「表示名（Rule名）」とする。
- RuleのDSL本文、データソース、パラメーターはマスター画面へ公開しない。
- Rule本体の作成・更新・テスト実行は引き続き `SYS_ADMIN` 限定とする。

## 2.5 法定控除の詳細参照

法定控除の詳細タブは、計算根拠となるDBデータを確認する読み取り専用画面とする。

| 詳細種別 | 参照内容 |
|---|---|
| `INCOME_TAX` | 現在年の所得税額表 |
| `RESIDENT_TAX` | 現在年度の従業員別・月別住民税 |
| `HEALTH_INSURANCE` | 現在年の健康保険料率 |
| `PENSION` | 標準報酬月額テーブル |
| `EMPLOYMENT_INSURANCE` | 現在年の雇用保険料率 |

- 詳細タブからの追加、更新、削除は行わない。
- 根拠マスターの更新は、それぞれの正式な取込・マスター管理機能に閉じる。
- 対象データがない場合は空表ではなく警告を表示する。
- 旧実装に存在した、バックエンドAPIを持たない汎用詳細CRUDは削除した。

## 4. テナント分離

- 一覧、詳細、コード検索、日次・月次の給与項目取得は `tenant_id` と `deleted_at is null` を明示条件にする。
- Ruleの存在確認と候補一覧も現在の `tenant_id` を明示条件にする。
- 別テナントのIDまたはコードを指定しても取得・更新できない。

## 5. 完全マスター駆動の確定方針

手当・控除の「種類」は単一の列にまとめず、次の独立した設定軸で定義する。項目コードによる画面・Java処理の条件分岐は追加しない。

### 5.1 適用対象

| 設定値 | 内容 | 例 |
|---|---|---|
| `ALL_EMPLOYEES` | 有効期間内の全従業員へ自動適用 | 勤務態度手当 |
| `EMPLOYEE_ENROLLMENT` | 従業員ごとに利用有無・有効期間・設定値を保持 | 寮費、携帯電話貸出料、Wi-Fi使用料 |

適用対象は手当・控除の別とは独立する。したがって、全員対象の控除、従業員別の手当も同じ基盤で表現できる。

### 5.2 入力・計算元

| 設定値 | 内容 |
|---|---|
| `DAILY_REPORT` | 日報で計算・入力して保存する |
| `TRANSACTION` | 明細到着や任意の支払・支給時に取引として登録する |
| `MONTHLY_CLOSING` | 月次Viewの集計結果を締め時に確定する |

計算方法は従来どおり`MANUAL`、`FIXED`、`AUTO`を使用し、入力・計算元とは分離する。

### 5.3 残高管理

| 設定 | 内容 |
|---|---|
| 残高管理なし | 日報または月次の金額だけを保存する |
| 残高管理あり | 発生、支払・支給、調整を台帳へ記録し、現在残高を算出する |

残高単位は`AMOUNT`、`DAYS`、`HOURS`、`COUNT`から選択する。手当と控除のどちらでも残高管理を使用できる。

- 残高を従業員テーブルの専用列へ追加しない。
- 残高は給与項目、従業員、発生日、取引種別、増減値、参照元を持つ汎用台帳から算出する。
- 明細取引の`balance_effect`は`CREDIT`（残高増加）、`DEBIT`（残高消化）、`NONE`（残高非連動）とする。
- 日報の手当・控除数量と確定済み明細取引は`vw_employee_payroll_item_balance_event`で同じイベント形式として参照できる。
- 締め処理済み明細を変更する場合は、既存取引を書き換えず調整取引を追加する。
- 従業員画面はマスター、ポリシー、入力項目定義からタブと入力欄を動的生成する。

### 5.4 従業員別パラメーター

寮タイプや徴収方式のような項目は、`DORMITORY_FEE`判定で画面へ直書きせず、パラメーター定義として管理する。

パラメーター定義は少なくとも次を保持する。

- キー、表示名、入力型
- 必須、初期値、表示順
- 選択肢
- Ruleへ渡すか
- 日報へ表示するか

パラメーターキーは単なる表示名ではなく、次のデータを結ぶ永続的な識別子である。

- `payroll_item_parameter_definition.parameter_key`
- 従業員別適用履歴の`employee_payroll_item_enrollment.settings_json`
- Ruleへ渡す項目別パラメーター
- Rule値Resolverの参照元キー

このため、新規入力項目の作成時だけキーを入力可能とし、保存済みのキーは変更不可とする。名称変更が必要な場合は表示名を変更する。意味の異なる項目へ置き換える場合は、既存定義を削除して新しいキーの定義を追加し、従業員別設定を改めて登録する。

画面から保存した定義は、次の順序で利用される。

1. 手当・控除マスター保存時にポリシーとパラメーター定義を同一トランザクションで保存する。
2. `EMPLOYEE_ENROLLMENT`の有効項目を従業員編集画面へ動的表示する。
3. 従業員が入力した値を型・必須・選択肢で検証し、有効期間付き設定JSONへ保存する。
4. 日報対象日に有効な設定を取得し、`ruleParameter=true`の値を対象マスターのRuleパラメーターへ合流する。
5. Resolver指定項目は従業員の直接入力値ではなく、同じポリシー内の参照元定義から計算値を解決する。

マスター保存時には、キー重複、選択肢の空値・値重複、初期値の型、入力元切替の形式、Resolver参照元と計算値を検証し、日報実行時まで設定不備を持ち越さない。

これにより、新しい手当・控除を追加してもフロントエンドとバックエンドへ項目コード固有の条件分岐を追加しない。

## 6. 日報・月次給与・締め処理の責務

### 6.1 日報

- 日次対象の手当・控除についてRule、固定値、手入力から当日の金額を決定する。
- 計算根拠、基準金額、最終金額、手動変更理由を日報明細へ保存する。
- 残高管理対象では、保存された日報明細を参照元とする残高取引を記録する。

### 6.2 月次View

- 日報に確定保存された手当・控除明細を対象期間で集計する。
- 確定済みの明細型取引を対象期間で集計する。
- 税額表や保険料率など、集合演算に適する法定控除を計算する。
- 項目コードごとの固定SQL列を増やさず、給与項目コード単位の行データとして集計する。
- JEXL、MVEL、Java BeanのRuleをMySQL View内では実行しない。日次Ruleは日報保存時、月次専用Ruleが必要な場合は締め処理の前処理で実行する。

### 6.3 締め処理

- 最新の月次Viewを入力とする。
- ストアドでViewから`historyTable`と`outputTable`へ同一バージョンの確定データを保存する。
- 再締めでは最新データから再集計し、履歴バージョンを増やす。
- 帳票は`historyTable`または`outputTable`の確定値を使用し、Ruleを再実行しない。

手当・控除は「日報だけの項目」ではなく給与計算を構成する汎用給与項目である。ただし、日次対象は日報で金額を確定し、月次対象は月次Viewでその保存値を集計する。残高台帳は給与計算結果とは分離して保持する。

## 7. 現行実装との差分

- 月次締めは現在も主に月次Viewで日報明細と確定取引を集計しており、この責務は維持する。
- `PayrollItemMonthlyInputService`は存在するが、現行の締め処理から実質的に利用されていない。月次Ruleが必要になるまで正規経路とはしない。
- `DORMITORY_FEE`の寮タイプ、徴収方式、日数入力はパラメーター定義へ移行済みである。
- 控除／手当マスターを作成しただけでは従業員別設定へ表示されない。マスター編集画面でポリシー、適用対象、入力元、残高、パラメーターを同時に登録する。
- 従業員別設定、日報、明細取引、残高照会は手当・控除の両方へ対応済みである。
- Ruleの実行時取得と参照チェックは`tenant_id`条件で統一済みである。

互換資産として残すもの：

- 旧`employee.dormitory_flag`、`employee.dormitory_type`：既存DB移行と旧APIレスポンスの互換用。新規計算・画面入力では参照しない。
- 旧`daily_report.dormitory_charge_days`：過去日報の読込用。新規数量は手当／控除明細の`quantity`を正規データとする。

## 11. 手動確認シナリオ

1. `master:view` のみを持つ利用者で手当・控除一覧と詳細を閲覧できる。
2. 同利用者には新規登録、保存、削除ボタンが表示されない。
3. `master:manage` を持つ利用者で新規登録できる。
4. 既存コードが編集不可である。
5. `AUTO` 選択時だけRuleプルダウンが表示される。
6. 無効なRuleをAPIへ直接送信すると400になる。
7. `FIXED` で固定金額未入力の場合は保存できない。
8. `MANUAL` は常に手入力可として保存され、`AUTO` / `FIXED` では「計算結果の手動変更を許可」を画面から設定できる。
9. 削除後に一覧から消えるが、DB行は論理削除で残る。
10. 所得税、住民税、健康保険、厚生年金、雇用保険の詳細タブで根拠データを参照できる。
