# V1後リファクタリング指針

## 1. 目的

V1で確定した業務仕様と利用者向けの挙動を維持しながら、既存資産を安全に整理する。

このフェーズでは次を優先する。

- 既存機能の責務と依存関係の整理
- 実務パターンを網羅する回帰テストの追加
- 帳票、台帳、締め処理、日報の変更容易性向上
- ローカルとAWSの環境差異の縮小
- 障害時に原因を特定できるログと検証手順の整備

原則として、新規業務機能の追加や確定済み仕様の変更は行わない。

## 2. 基準点

- V1基準タグ: `v1.0.0`
- V1後リファクタリング基幹ブランチ: `refactor/post-v1-stabilization`
- V1基準タグは、2026年10月31日にAWSへ反映した資産を示す。

問題が発生した場合は、必ず `v1.0.0` との差分から影響範囲を確認する。

## 3. 変更原則

### 3.1 挙動を変えない

- 画面表示、API形式、DB計算、帳票出力を同時に変更しない。
- 仕様変更が必要になった場合は、リファクタリングと別の変更として扱う。
- 既存の不具合を見つけても、整理と修正を同じ差分へ混在させない。
- 一時的な互換処理を削除する場合は、利用箇所が0件である証拠を残す。

### 3.2 小さく分割する

- 1コミット、1プルリクエストは1つの責務または1つの業務領域に限定する。
- 機械的な名称変更とロジック変更を分離する。
- 大規模な共通化より、重複箇所のテスト追加を先に行う。
- 作業途中の帳票、SQL、生成物をコミットしない。

### 3.3 データを壊さない

- DB変更は原則として追加的かつ再実行可能にする。
- 列削除、型縮小、データ補正などの破壊的変更は別途バックアップと移行計画を必須とする。
- AWS固有の実データをローカル用fixtureで上書きしない。
- 未登録、0件、NULL、再締め、既存データ混在を正常系のテスト対象に含める。

## 4. 優先順位

### 優先度A: 金額と確定データ

- 日次・週次・月次の支払日算出
- 日報から給与、手当、控除、貯蓄、借入への集計
- 自社締め、顧客締め、再締め、Version消費
- 給与明細、給与支払表、労務費一覧、請求書、注文書
- 課税対象額、社会保険、法定準備金、年末調整

### 優先度B: 帳票と台帳

- Jasper、HTMLプレビュー、Spreadsheet間の項目整合
- Working資産と実行資産の同期
- 印刷範囲、改ページ、列幅、罫線、単位、日付形式
- テンプレートとコード生成帳票の責務分離

### 優先度C: 管理・取込・分析

- マスターデータ取込の成功・失敗・再実行
- 応募者と応募媒体の連動
- 会社情報、休日管理、業務設定の未登録状態
- 外部サービスやAI分析の拡張は別フェーズとする。

## 5. テスト方針

### 5.1 先に現行挙動を固定する

リファクタリング前に、対象機能の現行挙動を特徴付けるテストを追加する。

最低限、次のケースを保持する。

- 日払い・日給者
- 週払い・日給者
- 月払い・日給者
- 日曜日、お盆、土曜日勤務、月次支払日の前倒し
- 支払日の手入力上書き
- 日報の遅延入力と同一支払日の複数日報
- 締め前、締め済み、再締め、既存入金済み取引
- 手当・控除マスターの動的項目
- 0円、負数、返金、引出、残額、累計額
- 会社情報や計算マスターが未登録の状態
- 当月、翌月、翌々月の入金予定

### 5.2 テストの役割

- 単体テスト: 計算、日付、分類、フォーマット
- Repository・SQLテスト: View、ストアド、集計境界、NULLと重複
- APIテスト: 権限、未登録、入力検証、エラー形式
- 結合テスト: 日報から締め・取引・台帳・帳票まで
- 帳票テスト: 必須文言、項目順、ページ数、テンプレート整合
- E2Eテスト: 利用者が行う主要操作のみ

カバレッジ率だけを目的にせず、金額、日付、確定データの分岐を優先する。

## 6. 実装領域ごとの指針

### バックエンド

- Controllerは認証、入力、レスポンス変換に限定する。
- 業務計算はServiceまたは明示的なCalculatorへ集約する。
- 帳票ごとの都合を日報や締めのコアロジックへ持ち込まない。
- 例外は利用者向けメッセージと運用ログを分ける。
- テナント条件をRepository引数とテストで明示する。

### フロントエンド

- API通信、状態管理、表示ロジックを分離する。
- 未登録と取得失敗、0件と通信失敗を区別する。
- 金額、時間、日付、単位の表示処理を共通化し、入力値とは分離する。
- 自動計算値を手入力で上書きできる項目は、上書き後の再計算条件を明示する。

### SQL・DB

- Viewとストアドは入力、出力、集計単位、丸め位置をコメントまたは仕様書へ残す。
- 同じ金額の定義を複数Viewへ複製する場合は、整合テストを追加する。
- runtime schema manifestと検証スクリプトを同時に更新する。
- ローカルfixtureは実データの初期登録処理として利用しない。

### 帳票・台帳

- `report-design/*/working`を編集元、`backend/src/main/resources`を実行資産として同期する。
- 同期前後のハッシュまたは差分を検証する。
- 帳票値の計算は可能な限りSQL/View側に寄せ、JRXMLとHTMLでは表示に専念する。
- レイアウト変更には必須文言、列、単位、改ページの自動テストを追加する。
- 締め時の保存帳票と最新データのHTMLプレビューを混同しない。

## 7. ブランチとコミット

- 基幹ブランチ: `refactor/post-v1-stabilization`
- 個別作業: `refactor/<領域>-<目的>`
- 不具合修正: `fix/<領域>-<原因>`
- テスト追加: `test/<領域>-<対象>`

コミットメッセージは、変更目的が判別できる単位にする。

例:

```text
test: cover weekly payroll payment-date boundaries
refactor: separate monthly invoice aggregation from rendering
fix: distinguish missing company profile from fetch failure
```

## 8. 完了条件

各変更は次を満たしてから統合する。

1. 変更前の挙動を示すテストがある。
2. バックエンドテスト、フロント型チェック、対象テストが成功する。
3. DB変更は再実行でき、検証SQLがある。
4. 帳票変更はWorking資産と実行資産が一致する。
5. ローカルとAWSで設定差異による挙動変化がない。
6. 失敗理由を画面またはログから判断できる。
7. `v1.0.0` から意図しない仕様差分がない。

## 9. 最初に行う作業

1. [主要業務フローとテストの対応表](post-v1-business-flow-test-matrix.md)を維持・更新する。
2. 日次・週次・月次の実務データfixtureを整理する。
3. 締め処理と帳票生成の結合テストを追加する。
4. 帳票Working資産の同期検証を自動化する。
5. Controller、Service、SQLに残る重複計算を棚卸しする。
6. AWSとローカルの初期データ・設定差異を一覧化する。
