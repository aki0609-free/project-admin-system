# 税金データ取込 V1

## 1. 目的

公的機関または自治体から受領した税金データをPythonで正規化し、
汎用外部データ取込基盤を経由して控除計算・控除詳細へ反映する。

## 2. 対象

| 税区分 | 元データ | 取得方法 | 取込先 |
|---|---|---|---|
| 所得税 | 国税庁「給与所得の源泉徴収税額表（月額表）」Excel | Pythonが公式URLから取得可能 | `income_tax_table` |
| 住民税 | 市区町村・eLTAXから届く特別徴収税額通知 | 管理者が電子データ・CSV/Excel・PDF等をアップロード | `resident_tax_monthly` |

税額に加えて、給与から控除する社会保険料も同じ検証単位で扱う。

| 社会保険区分 | 元データ | 2026年度の取込・計算状況 | 本番判定 |
|---|---|---|---|
| 健康保険 | 協会けんぽ都道府県別保険料額表PDF | 公式PDF変換・取込・給与View境界値テスト済み | 適用月と人手照合待ち |
| 介護保険 | 協会けんぽ保険料額表PDF | 公式PDF変換・対象フラグ・給与View計算済み | 適用年齢運用と人手照合待ち |
| 厚生年金 | 日本年金機構保険料額表PDF | 公式PDF変換・取込・給与View境界値テスト済み | 端数処理の最終確認待ち |
| 雇用保険 | 厚生労働省料率表PDF | 3事業区分の公式PDF変換・取込・給与View計算済み | 労働保険上の事業区分確定待ち |
| 子ども・子育て支援金 | 協会けんぽ保険料額表PDF | 公式PDF変換・取込・給与View境界値テスト済み | 適用月と人手照合待ち |
| 標準報酬月額 | 資格取得時決定・定時決定・随時改定 | `employee_standard_remuneration`を給与Viewが参照 | 従業員別履歴の登録運用テスト待ち |

`standard_salary_table`は保険料額表の等級範囲を保持する補助表であり、
月次給与計算が直接参照する確定マスターではない。毎月の総支給額から
標準報酬月額を引き直さず、決定・改定済みの従業員別履歴を使用する。

所得税・住民税は年度ごとに内容が変わり得るため、前年データを流用しない。

## 3. 所得税

Python資産：

```text
imports/scripts/convert_income_tax_table_v2.py
```

処理：

```text
国税庁公式.xls
  → 複数行ヘッダーと扶養人数0～7人の列を検出
  → year,minSalary,maxSalary,dependents,taxAmountへ正規化
  → UPSERT
  → 所得税控除詳細・月次給与明細の税額検索で参照
```

2026年版は1928行を生成する。給与範囲・扶養人数のキー重複を検出した場合は
取込せずエラーにする。

コンテナのPython依存関係には`.xls`読込用の`xlrd`を含める。

## 4. 住民税

### 4.1 会社が受け取る通知

給与から住民税を控除する特別徴収では、市区町村が会社（特別徴収義務者）へ
次の2種類を送付する。

| 通知 | 用途 | ProjectAdminでの扱い |
|---|---|---|
| 特別徴収義務者用 | 会社が従業員別・月別の徴収額を確認し、給与から控除する | 給与計算の取込元 |
| 納税義務者用 | 従業員本人への税額通知。会社が本人へ配付する | 給与計算の取込元にしない。将来の安全な配付機能の対象 |

普通徴収となった従業員の通知は原則として本人へ直接送付され、会社の給与控除
対象には含めない。給与支払報告書をeLTAXで提出した場合、特別徴収義務者用と
納税義務者用は、それぞれ電子データまたは書面を選択できる。受取方法は従業員
単位ではなく特別徴収義務者単位で選択される。

参考：

- [横浜市：特別徴収税額決定（変更）通知書の電子化について](https://www.city.yokohama.lg.jp/kurashi/koseki-zei-hoken/zeikin/jigyosya/shizei/choshu/tokuchozeitu.html)
- [川崎市：個人住民税等の給与からの特別徴収制度](https://www.city.kawasaki.jp/230/page/0000053359.html)

### 4.2 汎用取込方針

利用者にProjectAdmin専用CSVを毎年手入力させる運用を標準にしない。受領形式ごとの
Adapterで共通ステージング形式へ変換し、確認後に確定テーブルへ反映する。

```text
eLTAX電子データ ─┐
自治体CSV/Excel  ├→ 形式判定 → Format Adapter → 取込ステージング
PDF             ┤                              → 従業員突合・月額検証
紙のスキャン画像 ┘                              → 管理者確認
                                               → resident_tax_monthlyへ確定
```

| 入力形式 | 取込方法 | 人手確認 |
|---|---|---|
| eLTAX・自治体電子データ | 公式レイアウト用Adapterで直接変換 | 不一致・重複のみ |
| CSV/Excel | ヘッダー判定または列マッピングAdapter | 初回形式と不一致行 |
| PDF | テキスト抽出、必要時OCR、共通形式へ変換 | 全件または差分確認 |
| 紙 | スキャン後にOCR | 必須 |
| ProjectAdmin標準CSV・画面貼付 | フォールバック | 入力者と確認者を分離 |

PDF・紙はOCR誤認識の可能性があるため、無確認で給与控除へ反映しない。全形式で
原本ハッシュ、取込年度、受取自治体、変換結果、確認者、確定日時を監査証跡として
保存する。未知の自治体レイアウトを無条件に推測せず、未対応形式は列マッピング
画面または新しいAdapterで吸収する。

### 4.3 画面入力

電子データを入手できない場合や少人数の訂正に対応するため、SYS_ADMIN限定で
画面入力も許可する。画面入力も`resident_tax_monthly`へ直接反映せず、ファイル
取込と同じ取込ステージング、検証、管理者確定を経由する。

画面の入口は`手当・控除管理 > 住民税 > 住民税詳細`とする。既存の控除詳細表は
参照専用であるため、年度選択、取込、画面入力、検証、差分確認、確定を行える
住民税専用の全画面Editorへ遷移する。12か月×従業員の表を控除マスター編集
ダイアログ内へ詰め込まず、控除基盤の詳細機能として分離する。

```text
対象年度を選択
  → 従業員一覧（6月～翌年5月）
  → セル入力またはExcel範囲貼り付け
  → 検証
  → 差分確認
  → 確定
  → resident_tax_monthlyへ反映
```

画面要件：

- 年度は6月開始・翌年5月終了で表示する
- 従業員コード・氏名・自治体・受給者番号を表示する
- 6月のみ別額、7月以降同額を一括設定できる
- 12か月分のコピー＆ペースト、行コピー、前年度コピーを補助する
- 空欄（通知・設定なし）と0円（通知上0円）を区別する
- 負数、上限超過、重複従業員、対象外月、年間合計不一致をエラーにする
- ファイル取込値、画面入力値、現在の確定値の差分を表示する
- 入力者、確認者、入力元`MANUAL`、変更理由、確定日時を保存する
- 締め済み月の変更は通常保存せず、再締めが必要であることを警告する

従業員給与設定の`resident_tax_monthly`は通知データがない場合の暫定フォールバック
であり、正式な年度・月別税額の編集場所にはしない。通常運用では控除基盤の
住民税Editorから`resident_tax_monthly`を管理する。

少人数であっても、入力者が保存しただけで給与へ反映せず、確認・確定を独立させる。
同一管理者が両方を行えるV1運用でも、操作時刻と操作種別は分けて記録する。

#### 実装資産（2026-08-10）

| 区分 | 資産・エンドポイント |
|---|---|
| DB | `resident_tax_input_batch`、`resident_tax_input_row` |
| SQL | `sql/system/import/resident_tax_editor_foundation_v1.sql` |
| 参照 | `GET /api/master/deductions/resident-tax?fiscalYear={year}` |
| 下書き・検証 | `PUT /api/master/deductions/resident-tax/draft` |
| 確定 | `POST /api/master/deductions/resident-tax/{batchId}/confirm` |
| UI | `手当・控除管理 > 住民税 > 詳細情報 > 年度別住民税を編集` |

画面Editorでは年度別12か月入力、7月以降コピー、Excel範囲貼り付け、現在値との差分、
締め済み月表示、変更理由、確定を実装した。確定処理は差分だけを
`resident_tax_monthly`へ反映する。締め済み月の差分は再締め確認なしでは確定しない。

Testcontainersで次を確認済み：

1. 画面入力を下書き・検証し、12か月分を確定できる
2. 6月と7月以降の異なる税額を保持できる
3. 締め済み月の変更を再締め確認なしで拒否する
4. 確定した住民税が従業員給与設定の暫定月額より優先される
5. 月次給与計算Viewへ反映される
6. 月次締めストアド`sp_monthly_pay_slip_snapshot`を経由し、
   `monthly_pay_slip_history.resident_tax`へ締め時点の金額が固定される

2026年度8月の統合テストでは、従業員給与設定の暫定値を999円、住民税Editorの
確定値を12,000円に設定した。給与計算Viewと締め履歴はいずれも12,000円となり、
年度・月別住民税が正しく優先されることを確認した。

### 4.4 現在のCSV変換資産

Python資産：

```text
imports/scripts/convert_resident_tax.py
```

入力CSVで利用できる形式：

1. `employeeId,fiscalYear,month,taxAmount`の正規化済み形式
2. `社員ID,6月,7月以降`
3. `社員ID,月額`
4. `社員ID,1月,...,12月`

年度は6月開始・翌年5月終了として扱う。例：`fiscalYear=2026`は
2026年6月から2027年5月までである。

従業員の突合には内部`employeeId`を使用する。氏名だけでの自動突合は、
同姓同名や表記揺れによる誤控除を避けるため行わない。

本番運用では、自治体・eLTAXから取得したファイルをサーバーの任意フォルダへ
直接置かない。管理者が外部データ取込画面からアップロードし、次の順で処理する。

```text
通知原本
  → アップロード一時ファイル
  → 形式別Adapter／Python正規化
  → 取込ステージング
  → 管理者確認
  → resident_tax_monthlyへUPSERT
```

現在、アップロード原本は処理後に削除される。税額通知の監査証跡として、
本番適用前に原本・正規化CSV・取込結果を管理者限定S3領域へ保存する。

```text
documents/imports/tax/resident/{fiscalYear}/{executionId}/
  original/
  normalized/
  result/
```

実運用CSVは内部IDの手入力を避け、従業員コードから`employeeId`へ安全に
解決する方式へ拡張する。実際の通知ファイル形式は匿名化サンプルで確認する。

月次給与明細では次の優先順位で住民税を決定する。

```text
1. resident_tax_monthlyの対象年度・対象月
2. employee_payroll_profile.resident_tax_monthly
3. 0円
```

## 5. アップロード＋Python前処理

取込定義の`source_type=UPLOAD`でも`script_type=PYTHON`を指定できる。

```text
アップロード一時ファイル
  → ${IMPORT_INPUT_FILE}
  → Python前処理
  → ${IMPORT_CSV_DIR}の正規化CSV
  → Spring Batch
  → 許可済みテーブルへUPSERT
```

任意のコマンドや任意のテーブルは実行できない。スクリプトは設定済みの
import script領域、取込先はImport Target Catalogで許可されたものに限定する。

## 7. 社会保険料の版管理

保険料率の切替条件を給与Viewへ直接ハードコードしない。
`payroll_calculation_period`が対象月ごとに使用する料率版を指定する。

| 項目 | 内容 |
|---|---|
| `target_month` | 給与対象月の月初日 |
| `income_tax_year` | 使用する所得税表の暦年 |
| `insurance_rate_year` | 使用する社会保険料率の版 |
| `child_care_support_required` | 支援金適用有無 |
| `verified_flag` | 公式資料との照合完了 |
| `source_note` | 公式資料名・URL・確認者・確認日 |

`insurance_rate_year`はカラム名にyearを含むが、実質的には対象月が選択する
料率版である。2026年1月から3月に旧版、4月以降に2026年度版を割り当てる
ことができる。

雇用保険は一般・農林水産等・建設で料率が異なる。会社名や業務画面上の
職種から推定せず、労働保険関係成立票等で正式な事業区分を確認してから
本番マスターを確定する。

### 7.1 労働保険設定の管理単位

労働保険上の区分は`company_profile`の現在値1カラムに固定せず、会社・事業所と
適用期間を持つ`company_labor_insurance_setting`（仮称）で管理する。

```text
tenant_id
business_unit_id
employment_category
workers_compensation_type
effective_from
effective_to
rate_year
verified_flag
verified_at
verified_by
source_note
```

法定区分をRuleが業種名・職種名等から推測しない。管理者が正式な届出内容を登録し、
給与計算は対象月に有効な設定と年度別料率マスターを参照する。Ruleへは確定済み区分を
Factとして渡すことはできるが、区分の正本は期間付き設定とする。締め履歴には計算時点の
区分・料率版・適用料率を保存し、将来の料率改定後も過去計算を再現可能にする。

## 11. AWS反映用SQL資産

税・社会保険の取込定義は次の再実行可能SQLで管理する。

```text
sql/system/import/tax_import_foundation_v1.sql
```

このSQLはランタイムスキーママニフェストへ登録済みであり、次をUPSERTする。

- 所得税、住民税、健康保険、介護保険、厚生年金、雇用保険、支援金の取込定義
- 各取込CSVの許可カラムとキー
