# ProjectAdminSystem 詳細設計書作成ガイド

## 1. 目的

Codexの実装作業とは別に、通常チャットを使ってProjectAdminSystemの仕様とコードをドメイン単位で把握できる詳細設計書を作成する。

設計書は「画面の説明」だけではなく、次を追跡できる状態を完成条件とする。

- どの業務要件を実現する機能か
- 画面操作がどのAPIへ到達するか
- APIからService、Repository、DB資産までどう処理されるか
- View、Stored Procedure、Python、S3、メールなどの外部資産がどこで使われるか
- 変更時にどこへ影響するか
- どのテストが仕様を保証するか
- V1の制約とV2へ送る課題は何か

## 2. 基本ルール

### 2.1 コードを正として調査する

通常チャットへ過去の会話だけを渡して仕様書を書かせない。必ず現在の作業フォルダを読み取り、実装とDB資産を根拠にする。

```text
/Users/tatsukiakiyama/Documents/ProjectAdmin/public-repository
```

設計書には調査時点のブランチ名とコミットIDを記載する。未コミット変更がある場合は、その状態も記載する。

### 2.2 事実・推測・未決事項を分ける

記述には次の区分を使う。

| 区分 | 意味 |
|---|---|
| 確定仕様 | 利用者と合意済み、またはテストで固定された仕様 |
| 実装事実 | 現在のコード、DDL、設定から確認できた事実 |
| 推測 | 命名や周辺コードから推測した内容 |
| 未決事項 | コードだけでは決められず、確認が必要な内容 |
| V2候補 | V1には含めない将来課題 |

推測を確定仕様として書かない。矛盾を見つけた場合は、仕様書の中で勝手に統一せず一覧化する。

### 2.3 1回に1ドメインだけ扱う

複数ドメインを一度に説明すると、業務境界と依存関係が曖昧になる。最初は読み取り専用で調査し、仕様書のレビュー後にコード修正を別作業として行う。

### 2.4 通常チャットへコードを渡す方法

通常のChatGPTチャットは、ローカルの絶対パスを書くだけではファイルを読めない場合がある。詳細設計書を推測で作らせないため、次のいずれかで現在のコードを渡す。

1. GitHubの対象ブランチとコミットURLを共有し、Web参照を許可する
2. ドメイン単位のソース、SQL、テストをZIPにして添付する
3. Codexで先にファイル一覧とコード調査結果をMarkdown化し、その成果物を通常チャットへ添付する

添付範囲には、画面だけでなくController、Service、Repository、DTO、Entity、SQL、テスト、関連設定を含める。秘密情報、`.env`、Terraform state、秘密鍵は含めない。

通常チャットがコードへアクセスできない場合は、業務仕様の整理とレビューだけに使用し、クラスやメソッド単位の技術仕様を確定させない。

## 3. 推奨する作成順

次の順番なら、後続機能を理解するための前提を先に揃えられる。

1. 共通アーキテクチャ
   - モジュール構成
   - 認証、権限、テナント
   - 共通API、例外、監査、日時、ストレージ
   - VueのPage、Composable、API、共通UIの役割
2. 従業員管理
   - 他の給与・日報・帳票処理の中心となるため
3. 顧客・現場・取引管理
4. 日報管理
5. 手当・控除・Rule管理
6. 日次締め・月次締め・顧客締め
7. 帳票、プレビュー、台帳、バックアップ
8. メール、お知らせ、バッチ、外部データ取込
9. 書類管理とS3
10. インフラ、Terraform、CI/CD、起動停止、監視

最初の通常チャットでは、コード変更をせず「共通アーキテクチャ概要」を作る。その次に「従業員管理」を作る。締め処理や帳票から始めると、多数の前提ドメインを同時に追うことになるため避ける。

## 4. ドキュメントの格納単位

ドメインごとに次の構成で分割する。

```text
docs/specs/{domain}/
├── 00-overview.md
├── 01-business-rules.md
├── 02-frontend.md
├── 03-api-backend.md
├── 04-database-assets.md
├── 05-sequences.md
├── 06-tests-operations.md
└── 07-change-impact-known-issues.md
```

1ファイルを巨大化させず、業務仕様と技術仕様を相互リンクする。Confluenceへ転記する場合も、この単位を子ページとして使う。

## 5. 各ファイルに記載する内容

### 5.1 00-overview.md

- 目的、利用者、対象範囲、対象外
- 用語集
- メニュー、Router、権限コード
- 関係するドメインと依存方向
- 機能の全体フロー
- 調査ブランチ、コミットID、作成日

### 5.2 01-business-rules.md

- 登録、更新、削除、検索の業務条件
- 状態遷移
- 日付、締日、金額、丸め、重複防止
- 再処理、取消、論理削除
- テナント境界
- V1固有仕様とFuyo固有仕様

Fuyo固有仕様はCore仕様と混ぜず、`docs/kb/fuyo/`の資料へリンクする。

### 5.3 02-frontend.md

- 画面URL、Router定義、メニュー定義
- Page、Tab、Dialog、Form、Table、Toolbarの構成
- PageからComposable、APIクライアントまでの呼出順
- Props、Emits、主要なstate、computed、watch
- Query／Mutationのキャッシュキーと再取得条件
- 入力検証、エラー表示、ローディング、二重送信防止
- 共通UIとドメイン固有UIの境界
- 主要ファイルの絶対パス、コンポーネント名、関数名

コード全文は貼らない。重要な分岐や副作用は、ファイルと関数を示して日本語で説明する。

### 5.4 03-api-backend.md

- API一覧（Method、Path、権限、Request、Response、Status）
- ControllerからService、Domain、Repositoryまでの呼出順
- DTO変換とValidation
- Transaction境界
- 例外とエラーレスポンス
- 認証ユーザー、テナントID、監査情報の取得元
- 冪等性、同時実行、排他、再試行
- 主要クラス、メソッド、絶対パス

### 5.5 04-database-assets.md

- テーブル、主キー、外部キー、ユニーク制約、Index
- 論理削除、監査、テナントカラム
- Entityとの対応
- View、Stored Procedure、Function、初期データ
- Python取込資産と入出力
- Hibernate `ddl-auto`で作る範囲と、明示的に配置するDB資産の境界
- マスター値の意味と参照元

### 5.6 05-sequences.md

最低限、次をMermaid sequence diagramで作る。

- 一覧表示
- 新規登録
- 更新
- 削除または無効化
- 主要な業務処理
- バッチ、締め、帳票など非同期処理

分岐が重要な場合だけフローチャートを追加する。

### 5.7 06-tests-operations.md

- 単体、Repository、Testcontainers、Playwrightの対象
- 正常、境界値、異常、権限、テナント分離、時系列のテスト表
- テストデータ作成方法
- 実行コマンド
- ログ、CloudWatch、アラーム、障害調査手順
- AWSとローカルの差異
- 起動、停止、再デプロイ、ロールバック

### 5.8 07-change-impact-known-issues.md

- 変更時の影響マップ
- 参照元、参照先、外部連携
- 既知の不整合、技術的負債
- V1リリース前の必須課題
- V2候補
- コードと仕様が一致しない箇所

## 6. コードを細かく把握する調査手順

各ドメインで次の順に追う。

1. Routerとメニューから画面の入口を特定する
2. Pageが読み込むTab、Dialog、Composableを列挙する
3. ユーザー操作ごとにイベントとMutationを追う
4. APIパスからControllerを検索する
5. ControllerからService、Repositoryを追う
6. DTO、Entity、Mapper、Validatorを確認する
7. RepositoryのJPQL／SQLとDBテーブルを対応させる
8. View、Stored Procedure、初期データ、Pythonがあれば追う
9. 関連テストから実際に保証されている振る舞いを確認する
10. 設定値、環境変数、AWS資産まで到達経路を追う

各重要処理について、次の形式で記録する。

| 項目 | 記載内容 |
|---|---|
| 起点 | 画面操作、バッチ、API |
| フロント | Page → Composable → API関数 |
| API | Method、Path、Request、Response |
| バックエンド | Controller → Service → Repository |
| DB | Table／View／Stored Procedure |
| 副作用 | S3、メール、履歴、ログ、別テーブル更新 |
| 保証テスト | テストファイル、テストケース名 |
| 失敗時 | Transaction、ロールバック、再試行、エラー表示 |

## 7. 通常チャットへ渡す最初の依頼

最初は共通アーキテクチャの調査だけを依頼する。

```text
ProjectAdminSystem V1の詳細設計書を、現在のコードを根拠に作成してください。

作業フォルダ：
/Users/tatsukiakiyama/Documents/ProjectAdmin/public-repository

今回はコードを変更せず、共通アーキテクチャだけを読み取り調査してください。
現在のブランチ、コミットID、未コミット変更の有無を最初に確認してください。

対象：
- backend/frontend/infrastructureの全体構成
- 認証、権限、テナント、監査、例外、Clock、Storageの共通基盤
- VueのPage、Composable、API、共通UIの基本構造
- ローカルDocker、AWS、Terraform、CI/CDの関係

出力先：
docs/specs/architecture/

最低限、次を作成してください。
- 00-overview.md
- 02-frontend.md
- 03-api-backend.md
- 04-database-assets.md
- 05-sequences.md
- 06-tests-operations.md
- 07-change-impact-known-issues.md

ルール：
- 過去会話の記憶ではなく現在のコードを正とする
- 確定仕様、実装事実、推測、未決事項、V2候補を区別する
- 主要ファイルは絶対パス、クラス名、関数名まで記載する
- コード全文の転載ではなく、呼出関係と重要な分岐を説明する
- Mermaidは依存関係や処理順が文章より明確になる箇所だけに使う
- 不整合を見つけても今回は修正せず、影響範囲と候補を記録する
- 作成後、私が読むべき順番と確認質問を提示する
```

```text

対象の入口：従業員管理メニュー
出力先：docs/specs/employee/

00～07の全ファイルを作成し、特に次を詳しく追ってください。
- 従業員の登録、更新、退職、検索
- 社員コードの採番と重複防止
- 契約、給与・税金、手当・控除設定
- 貸付、積立、汎用控除取引との関係

```

## 9. レビュー方法

設計書完成後、次の順でレビューする。

1. 業務用語と業務ルールが実運用と一致するかを利用者が確認
2. API、クラス、テーブル名が現在のコードと一致するかを再検索
3. 主要シーケンスを画面操作またはテストで再現
4. 未決事項へ回答し、確定仕様へ移す
5. 仕様と実装の差分をリファクタリング課題へ登録
6. コミットIDを更新し、Confluenceへ公開

設計書は一度作って完了ではない。ドメインの変更コミットと同時に、該当する設計書とKBも更新する。

## 10. 完成判定

次をすべて満たした場合、そのドメインを「把握可能な設計書」と判定する。

- 画面操作からDB更新まで自分で説明できる
- 主要クラスとファイルを迷わず開ける
- 業務ルールの実装場所が分かる
- View、Stored Procedure、Python、S3などの境界が分かる
- 変更時の影響範囲を列挙できる
- 正常系だけでなく失敗時の挙動が分かる
- 仕様を保証するテストと不足テストが分かる
- Fuyo固有仕様とCoreの汎用仕様を分離して説明できる
