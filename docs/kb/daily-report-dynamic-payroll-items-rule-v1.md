# 日報：動的手当・控除／Rule計算 V1

## 1. 目的

手当・控除マスターの設定に基づき、日報画面へ入力項目を動的に追加する。

`AUTO`項目はRuleで計算し、画面で結果を確認できるようにする。日報保存時には同じ計算をサーバー側で再実行し、改ざんされていないマスター情報と計算結果を保存する。

## 2. 対象範囲

今回の対象：

- 日報対象の手当・控除マスター抽出
- `MANUAL`、`FIXED`、`AUTO`の画面表示
- 日報入力内容を使ったRuleプレビュー
- 日報保存時の再計算
- 手当・控除明細のスナップショット保存
- 手当合計・控除合計・支給見込の再計算

今回の対象外：

- 月次手当・控除
- `PAYROLL` Rule
- 月次締め
- 給与確定
- 承認ワークフローと承認済み日報の凍結（V2）
- 給与明細生成

## 3. 日報へ表示するマスター

以下をすべて満たす手当・控除だけを日報対象とする。

- 現在のテナントに属する
- `deleted_at is null`
- `enabled = true`
- `show_on_daily_statement = true`
- 単位が `DAILY` または `BOTH`

`MONTHLY`および`PAYROLL`は日報画面へ表示しない。

## 4. 計算区分

| 区分 | 画面 | 保存時 |
|---|---|---|
| `MANUAL` | 入力可能。初期値はマスター初期金額 | 入力値を検証して保存 |
| `FIXED` | マスター固定金額を表示。編集不可 | マスターから再計算 |
| `AUTO` | Rule計算結果を表示。編集不可 | Ruleを再実行 |

- `AUTO`や`FIXED`の金額をブラウザ上で変更しても保存値には使用しない。
- 負数は保存しない。
- 下限・上限金額は共通給与項目計算サービスで適用する。
- Rule失敗時は0円で継続せず、プレビューまたは日報保存を失敗させる。

## 5. Rule種別

手当マスターから選択できるRule：

- `ALLOWANCE`
- `GENERAL`

控除マスターから選択できるRule：

- `DEDUCTION`
- `GENERAL`

`DAILY_REPORT`、`MONTHLY_DETAIL`、`PAYROLL`など用途が異なるRuleは候補に表示せず、APIへ直接指定しても保存時に拒否する。

## 7. dailyReportIdをRuleへ渡さない理由

新規登録の画面プレビュー時点では日報IDが存在しない。

プレビューと保存で同じRule結果を保証するため、日次Ruleは保存済み日報を再検索せず、リクエストから構築したパラメータだけで計算する。

日報自身のIDや保存済み手当・控除明細を参照するRuleは作成しない。

## 8. API

### 入力項目プレビュー

```text
POST /api/daily-reports/input-items/preview
```

リクエスト：

- `DailyReportSaveRequest`
- 現在画面に入力されている手当・控除を含む

レスポンス：

- 動的手当一覧
- 動的控除一覧
- 入力方式
- 計算金額
- 編集可否
- 表示順

画面では、従業員・勤務日・勤務時間・現場・走行距離・有給などが変わったとき、400ミリ秒待って再計算する。

## 9. 保存処理

1. 日報リクエストを検証する。
2. 従業員と雇用契約を取得する。
3. 日報本体へ勤務・請求情報を反映する。
4. 現在有効な日報対象手当・控除をマスターから取得する。
5. `MANUAL`はマスターIDで入力値を対応付ける。
6. `FIXED`はマスター固定金額を使用する。
7. `AUTO`はRuleを再実行する。
8. コード・名称はマスターから取得する。
9. 手当・控除の合計を日報本体へ設定する。
10. 支給見込・差引見込を再計算する。
11. 手当・控除明細をスナップショット保存する。

すべて同一トランザクションで処理する。Rule計算または明細保存に失敗した場合、日報本体を含めてロールバックする。

## 10. クライアント値を信用しない項目

以下は保存時にサーバー側で確定する。

- 手当・控除マスターIDの有効性
- 手当・控除コード
- 手当・控除名称
- 計算区分
- 編集可否
- `FIXED`金額
- `AUTO`金額
- 表示順
- 手当合計
- 控除合計
- 支給見込
- 差引見込

同じマスターIDがリクエスト内に複数存在する場合は不正リクエストとして拒否する。

## 11. 既知の懸念・後続対応

### 承認済み日報

V1では承認フローを使用しない。日報の新規作成・更新時は、画面やAPIから渡された承認状態にかかわらず、バックエンドで `APPROVED` を設定して保存する。承認コメントは保存しない。

日報編集画面には承認状態と承認コメントの入力欄を表示しない。検索結果の承認状態は既存データ確認と将来互換のため維持する。

承認申請、承認・却下、承認履歴、権限制御、承認済み日報と計算済み明細の凍結はV2で実装する。V2導入時には、承認前の再計算と承認後のスナップショット維持を分離する。

### マスター変更後の過去日報

V1では日報を編集・保存すると、現在有効なマスターとRuleで手当・控除明細を再構築する。V2の承認フロー導入後は、承認済み日報を編集不可にして保存済みスナップショットを維持する。

### Ruleの入力契約

日報からRuleへ渡すコンテキストキーは、V1では本KBのキーを正式な固定契約とする。新しいキーを利用する場合は、日報コンテキスト生成処理と本KBを同時に変更する。

Ruleマスターは固定契約の中から必要なパラメータを定義し、型、必須、既定値、表示順をRuleごとに設定できる。Ruleに設定した許可済みデータソースとFactの列マッピングもRuleごとに変更できるため、計算式と業務データ参照はマスター駆動とする。

汎用Rule実行APIとRuleテスト画面は任意キーのパラメータMapを受け取れるが、日報保存処理から渡す値は固定契約に限定する。V2でコンテキストキー自体を管理画面から追加する場合は、キー名、型、取得元、利用可能ドメインを管理するコンテキストカタログを別途設計する。

### 月次・給与計算

`MONTHLY`、`BOTH`の月次側処理、`PAYROLL`は、従業員管理・顧客管理のリファクタリング後に月次締めドメインで実装する。

## 12. 確認結果

- バックエンド全テスト：成功
- 日報コンテキスト／手入力引継ぎテスト：成功
- `AUTO`・`FIXED`編集不可テスト：成功
- フロントエンド対象Lint：成功
- フロントエンド本番ビルド：成功

## 13. 手動確認

1. `DAILY`または`BOTH`の日報表示対象マスターを登録する。
2. `MANUAL`、`FIXED`、`AUTO`をそれぞれ作成する。
3. `AUTO`へ用途が一致するRuleを割り当てる。
4. 日報を新規作成し、手当・控除タブへ3種類が表示されることを確認する。
5. 勤務時間などを変更し、`AUTO`金額が再計算されることを確認する。
6. `MANUAL`金額を入力し、別項目の再計算後も値が維持されることを確認する。
7. `FIXED`と`AUTO`が編集不可であることを確認する。
8. 日報を保存し、再表示後も明細と合計が一致することを確認する。
9. Ruleを意図的に失敗させ、日報が保存されないことを確認する。
