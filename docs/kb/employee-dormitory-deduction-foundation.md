# 従業員入寮情報・寮費控除 V1設計

## 1. 目的

従業員の入寮状態と寮タイプを管理し、適用日数と従業員別日額から当月寮費を発生させる。日報には実際に徴収した金額を入力し、未徴収金額を翌月へ繰り越す。例外的に月1回で徴収する従業員は、共通の明細型・月次型控除取引基盤を利用する。

## 2. 従業員項目

| 画面項目 | DBカラム | 値 |
| --- | --- | --- |
| 入寮あり | 従業員別控除設定 | `true` / `false` |
| 寮タイプ | `parameters.dormitoryType` | `SINGLE_ROOM` / `SHARED_ROOM` |
| 徴収方式 | `parameters.inputSource` | `DAILY_REPORT` / `TRANSACTION` |
| 寮費日額 | `parameters.dormitoryDailyAmount` | 寮タイプ選択時に解決して有効期間付きで保存 |

- 入寮なしの場合、寮タイプは未設定にする。
- 入寮ありの場合、寮タイプは必須とする。
- `employee.dormitory_flag` と `employee.dormitory_type` は既存コードとの互換用に同期するが、新規機能の判定元は従業員別控除設定とする。

## 3. 寮費を従業員マスターへ持たせない理由

寮費は業務ルールであり、将来の金額変更、会社別設定、寮タイプ追加に対応する必要がある。

従業員マスターには判定材料だけを保持し、金額は次の共通基盤で管理する。

```text
控除マスター → 従業員別適用設定 → 金額残高発生 → 日報／明細で実徴収
```

## 4. 残高発生ルール

寮費には、コード固有ではない次の汎用ルールを設定する。

```text
CALENDAR_DAYS_TIMES_PARAMETER:dormitoryDailyAmount
```

当月発生額は次の式になる。

```text
当月の適用日数 × 従業員別設定に保存した dormitoryDailyAmount
```

選択した寮タイプの計算値から日額を解決し、従業員別適用履歴へ保存する。後日マスターの日額を変更しても、過去期間の単価を勝手に書き換えない。

## 5. 日報での徴収

日報では「何日分」ではなく、その日に実際に徴収した金額を入力する。日報控除明細の `amount` と残高消化量 `quantity` はともに円単位となる。

- 通常日：その日に徴収した金額を入力する
- 土日・長期休暇前：複数日相当をまとめて徴収した金額を入力できる
- 徴収できない日：0円または未入力とし、未徴収金額を残す
- 月1回徴収：従業員別入力元を `TRANSACTION` にして明細画面から登録する

## 6. 単位変更の制御

寮費コード専用のバリデーションは設けない。残高発生ルールと単位の一般的な整合性として、次を検証する。

- `CALENDAR_DAYS_IN_ENROLLMENT` は `DAYS` 必須
- `CALENDAR_DAYS_TIMES_PARAMETER:{parameterKey}` は `AMOUNT` 必須

## 7. 日次・月次の処理

1. 対象月の適用日数と有効期間付き日額から当月発生額を計算する。
2. 日報または明細取引へ実徴収額を保存する。
3. 発生額から実徴収額を差し引き、未徴収金額を算出する。
4. 未徴収金額は繰越設定に従って翌月へ引き継ぐ。
5. 月次帳票は確定済み日報と確定済み明細取引の実徴収額を集計する。

残高発生額は未徴収残高の管理に使用し、給与控除へ二重計上しない。月次給与には日報または明細取引へ保存した実徴収額だけを反映する。詳細は `payroll-item-transaction-deduction-foundation.md` を参照する。

## 8. Rule基盤の柔軟性

Rule呼出しは `Map<String, Object>` でパラメータを受け取り、Ruleマスター側で次を設定できる。

- パラメータ名
- データ型
- 必須／任意
- 初期値
- JEXL／MVEL／Java Beanの実装方式

そのため、日額や計算式の変更は原則としてアプリケーションの再ビルドなしで行える。一方、新しい業務事実を画面入力・DB保存する場合は、DTO・Entity・標準コンテキストへの追加が1回必要になる。任意のテーブルやカラムを無制限に参照させないのは、SQLインジェクションと情報漏えいを防ぐための意図した制限である。
