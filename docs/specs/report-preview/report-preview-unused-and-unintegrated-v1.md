# 帳票Preview共通基盤 未使用・未連携・不整合調査 V1

## 1. 最新Previewと締め確定ファイルの差

月次・顧客締めのHTML Previewは最新Viewを読む一方、本印刷は締め時保存ファイルを読む。仕様上の使い分けだが、画面上で「簡易Preview（最新）」と「確定版印刷」を明示しないと同一内容に見える。

特に顧客別締日では、Preview Viewが暦月条件で集計されている帳票がある場合、顧客締め期間と一致しない可能性がある。顧客締めPreview Viewへ`periodFrom/periodTo`または確定Versionを渡す設計を優先課題とする。

## 2. `BOOK`は共通Tabへ未接続

`OperationType.BOOK`と`EXCEL_BOOK`は型として存在するが、`/operation/book`は専用の台帳生成・編集画面を使用し、`OperationReportTab`を使用しない。台帳は複数Sheet編集や対象者選択が必要な特殊画面のため、V1では意図した分離とする。

## 3. 表示許可・除外は画面側フィルター

月次画面は請求書・注文書を除外し、顧客締め画面はそれだけを許可するが、APIは`MONTHLY`の全定義を返す。権限・実行可否の境界ではなく表示整理に過ぎない。誤実行防止を強化する場合はサーバーで業務Scopeを区別する。

## 4. Preview定義の管理画面がない

定義と列はSQL資産で登録され、業務管理画面から編集できない。V1では配置資産として固定する。将来管理画面を追加する場合も、任意表名・並び順SQLを利用者へ直接入力させず、データソースCatalog方式を推奨する。

## 5. 列の自動推測

列定義がない場合は先頭行を基準に技術列を除外する。この場合、0件では列を確定できず、英語列名や意図しない順序になる可能性がある。本番帳票は列定義必須に寄せる。

## 6. tenantの既定値

対応済み。tenant IDの値として`default`は正式に許可するが、Tenant Contextが未設定または空の場合は`default`へ暗黙補完せず、Previewを拒否する。これにより現行の`default` tenantは表示でき、認証・Context設定漏れによるtenant境界の誤りだけを防止する。

## 7. SQL識別子の安全性

表名・列名・並び順には許可文字検証があり、値はNamed Parameterで渡す。直接的なSQL Injection対策はあるが、存在を許可したViewだけに限定するCatalog/allow-listではない。DB定義を信頼境界とすることを明記する。

## 8. 全有効定義のReadiness検証

対応済み。従来の日次必須2定義に加え、台帳専用画面を除く全有効定義について、起動時に次を一括検証する。

- データ元View/Tableの存在
- 対象日・対象月を絞り込む列の存在
- 登録済み表示列がデータ元に存在すること
- PDF/CSV/Excel/個別処理に対応する有効なBatch Jobの存在

不整合は対象tenant・Operation・帳票コードを列挙して起動を中止する。HTML/Jasper Templateの実体はS3・Local Storageの一時障害と設定不備を区別するため、アプリ全体の起動条件にはせず、対象帳票のPreview・出力時に個別検証する。`BOOK`は専用台帳基盤で検証するため共通Previewの検証対象外とする。

## 9. V1判断
