# 顧客請求締め 未使用・未連携・不整合調査 V1

## 1. 消費税率がJava固定

概算Serviceは10%を`V1_TAX_RATE`として固定する。帳票history側の税計算と同じ設定を参照しない場合、税率変更・軽減税率・期間変更で一覧と確定帳票が不一致になる。会社/税率の期間付きマスターを正本にする。

## 2. 概算SQLと帳票Viewの二重計算

画面概算は`CustomerBillingSummaryService`内SQL、確定帳票はView→history/outputで計算する。丸め、MONTHLY単価、その他金額等が片方だけ変わる危険がある。概算も同じ集計Viewを参照することを推奨する。

ここでいう「View共通化」は、概算専用Viewをもう1本作ることではない。請求金額・税率・端数処理を計算する行形式の共通Viewを正本にし、画面概算と締め保存用Viewの両方がそれを参照する構成を指す。画面と本印刷で金額が異なる事故を防ぐため、V1安定化対象とする。

## 3. HTML Previewの期間（2026-09-07 対応済み）

帳票タブで顧客を選択し、共通Previewへ`customerId / periodFrom / periodTo`を渡す。請求書は顧客固有期間の最新日報、注文書は対象月＋顧客の確定履歴を表示する。本印刷の保存済みファイルも`targetId`で限定する。

## 4. 失敗状態・実行履歴が自社月次より弱い

顧客締めは1社単位Transactionで原子的に処理するが、自社月次の`monthly_closing_executions/items`相当のPROCESSING/FAILED履歴を持たない。失敗時はDBが巻き戻っても、Transaction外のStorageファイルが孤立する可能性がある。

V1ではTransactionによるDB整合性と運用ログで対応し、専用の失敗実行履歴・再開機構・孤立ファイル自動cleanupはV2へ延期する。

## 5. `closed_by`未設定（2026-09-07 対応済み）

締め完了時に認証ユーザー名を保存する。認証主体がないシステム実行は`SYSTEM`とする。

## 6. 個別早期締め

個別締めは締日前でも実行可能で、全顧客締めだけが締日前を除外する。業務上の例外として意図した仕様だが、早期締め理由・実行者は保存されない。少なくとも確認表示と監査ログを残す。

## 7. Versionとファイル検索

顧客ごとにVersionが違うため、帳票タブは`closingVersion=null + allowMixedClosingVersions`で最新を取得する。過去Versionを画面から明示選択するUIはない。監査・再送要件がある場合は顧客/Version選択を追加する。

## 8. 注文書生成単位

現行Jobは顧客単位で注文書を生成する。仕様上「現場をまとめて請求額を決める」ため、帳票Viewが複数現場を正しく集約・明細化することを帳票Testcontainersで固定する。

## 9. V1判断

| 優先度 | 課題 | 推奨 |
|---|---|---|
| 高 | 税率・丸め・概算の二重ロジック | 確定Viewと共通化 |
| 対応済 | 顧客締めPreview期間 | 顧客固有期間へ一致 |
| 対応済 | `closed_by` | 認証ユーザー保存 |
| V2 | 失敗実行・孤立ファイル | 専用実行履歴・再開・cleanupを追加 |
| 中 | 過去Version選択 | V1運用確認後にUI判断 |
| 継続 | 早期締め理由 | 監査要件と合わせて追加 |
