# 日報管理 未使用・未連携・不整合調査 V1

ドメイン：日報管理

## 1. 目的

日報画面と保存処理について、現在のコードで「入力できるが使われない」「別計算経路と一致しない」「業務上必要な検証が不足している」箇所を整理する。本資料は直ちに削除する指示ではなく、V1安定化の判断材料である。

## 2. 高優先度：月次勤怠の給与概算が正式Ruleと異なる

`DailyReportMonthlyAttendanceQueryService`は保存済みの次の計算結果を使わず、給与区分ごとの簡易式で`grossSalaryAmount`を再計算する。

- `normal_pay_amount`
- `overtime_pay_amount`
- `night_pay_amount`
- `holiday_pay_amount`

特に時給者は`通常時間 + 残業時間 + 深夜時間`へ時給を掛けている。深夜時間は通常・残業・休日時間と重複可能なため、二重計上になり得る。

月給者も月給をそのまま返すため、日報単位のRule計算と意味が異なる。月次勤怠タブの概算を正式給与と誤認しないよう、V1では次のいずれかが必要である。

1. 保存済みRule結果の合算へ統一する。
2. 「参考概算」と明示し、正式締め結果との差異を許容する。

推奨は1である。

## 3. 高優先度：休日時間が月次勤怠レスポンスへ設定されない

フロント型`DailyReportMonthlyAttendanceResponse`には`totalHolidayWorkHours`があるが、バックエンドServiceは集計もbuilder設定もしていない。画面上では0または欠損扱いになる。

## 4. 高優先度：勤務時間の正本検証がフロント依存

開始・終了・休憩から通常・残業・深夜時間を作る処理はフロントにある。サーバーは次だけを検証する。

- 休憩分が0〜1440
- 各時間が0以上

次の整合性はサーバーで検証しない。

- 開始・終了と勤務時間が一致するか
- 休憩が勤務区間を超えていないか
- 通常・残業・休日時間の合計が実勤務時間と一致するか
- 深夜時間が勤務区間内か

API直接呼出や将来の別UIから不整合値を保存できるため、V1安定化ではサーバー側共通計算または検証を追加することを推奨する。

## 5. 有給残は表示だけで自動更新されない

`paidLeaveDays`は保存・月次集計・帳票連携されるが、日報保存時に従業員の有給残を減算しない。更新・削除時の戻し処理もない。

現状の「使用後残」は画面上の計算値であり、給与プロフィールの残高正本を変更しない。V1で残日数管理を正本化するなら、貸付・貯蓄と同様の差分更新または有給付与・消化取引テーブルが必要である。

## 6. 未入力者判定の対象が広すぎる

未入力者APIは未削除の全従業員を対象とし、次を考慮しない。

- 入社日・退職日・在籍状態
- 支払サイクル
- 勤務予定・休日
- 有給・休業

そのため、本来勤務しない従業員も未入力に表示される可能性がある。

## 7. 旧互換項目`dormitoryChargeDays`

`dormitoryChargeDays`はForm model、保存request、Entity、Validatorに残るが、現行の画面項目定義には表示されない。現在の寮費日数は動的控除明細の`quantity`で管理する。

これは旧データ移行との互換用であり、二重管理を避けるため新規ロジックでは使わない。移行完了と本番データ確認後に廃止可否を判断する。

## 8. 承認requestは実処理で無視される

フロント型とrequestに`approvalStatus`、`approvalComment`が残るが、Mapperは無視し、常に`APPROVED / NULL`を設定する。

V1方針と整合するためバグではないが、API契約だけを見ると更新できるように見える。V1ではrequestから除外するか、OpenAPI説明で「入力無効」と明記すると誤用を防げる。

## 9. 顧客名・現場名・職種名のrequest値

フロントは名称も送るが、顧客・現場名称と請求単価名称はサーバーがID・単価マスターから再解決する。requestの名称は正本ではない。

APIを簡素化するなら、保存requestから次の名称項目を削減できる可能性がある。

- `customerName`
- `siteName`
- `jobName`
- `siteRoleName`

ただし、現場なしで職種等を任意保存する既存データ要件を確認してから行う。

## 10. 現場なし時の職種・役職値

現場がない場合、請求単価Snapshotはクリアされる。一方、Mapperがrequestの職種・役職を先に設定するため、請求対象外の日報に職種・役職文字列だけが残る可能性がある。

仕様として「現場なしでも職種を記録する」なら維持できるが、「職種・役職は請求単価の属性」なら同時にクリアすべきである。

## 11. Java側に残る給与制度の固定値

Rule名と計算式はマスター・Rule駆動だが、次の値は`DailyPayComponentCalculationService`に固定される。

- 週法定時間：40時間
- 月60時間超判定
- 週の起算日：月曜日
- 残業率1.25、60時間超1.50
- 深夜率0.25、休日率1.35
- 日給の時給換算：8時間

Ruleへ変数として渡すため式側で利用できるが、企業設定や適用期間付きマスターからは取得していない。汎用Coreを目指す場合は会社・年度設定への移行課題である。

## 12. 一覧APIと画面検索の役割重複

一覧APIは日付・従業員絞込に対応するが、現行画面は全件取得してフロントで検索する。日報件数が増えるほど初期通信・ブラウザ負荷が増える。

V1の小規模運用では動作可能だが、期間指定をAPIへ渡す方式へ統一する方が安定する。

## 13. 手当・控除明細の全置換

更新時、既存明細を削除してサーバー再計算結果を再登録する。計算結果と日報の整合性を保ちやすい一方、明細IDは更新ごとに変わり、行単位の履歴ではない。

変更履歴が必要な場合は、日報確定履歴または監査ログへ別途保存する必要がある。

## 14. テスト状況

日報にはRule計算、Mapper、顧客・現場解決、入力項目、残高、Validator等の単体・Testcontainersテストがある。一方、次は追加価値が高い。

- 画面入力から保存、月次締め、給与明細までの時系列E2E
- 月末・締日跨ぎ
- 週40時間・月60時間の境界
- 日報更新・削除時の貸付貯蓄と給与項目残高の復元
- 有給残の仕様確定後の差分テスト
- 請求単価の適用期間切替・再保存

## 15. V1判断一覧

| 優先度 | 課題 | 推奨 |
|---|---|---|
| 高 | 月次勤怠概算と正式Rule結果が不一致 | 保存済み給与本体4区分の合算へ統一 |
| 高 | 休日時間合計が月次レスポンスにない | 集計・レスポンス設定を追加 |
| 高 | 勤務時間整合性がフロント依存 | サーバー共通計算・検証を追加 |
| 高 | 有給残が更新されない | V1運用を明記するか取引方式を実装 |
| 中 | 未入力者に非勤務者が含まれる | 在籍・勤務対象条件を追加 |
| 中 | 給与制度固定値がJavaにある | 会社・期間付き設定への移行設計 |
| 中 | 全件取得 | API期間検索へ統一 |
| 低 | 旧寮費日数・承認request | V1後の互換整理候補 |
